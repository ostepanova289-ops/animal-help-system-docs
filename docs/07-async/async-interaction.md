# Асинхронное взаимодействие в системе

## Выбранный сценарий

Обработка результата пожертвования после оплаты через внешний платёжный шлюз.

Суть сценария такая. Пользователь на сайте делает пожертвование и его переводят в платёжный сервис. Система сама не хранит данные карты, поэтому вся оплата проходит через внешний шлюз. В этот момент нельзя сразу понять, прошёл платёж или нет. Итог приходит позже от платёжного сервиса и уже тогда система обновляет статус пожертвования.

Это асинхронное взаимодействие, потому что платёж обрабатывает внешняя система и мы не контролируем, когда она вернёт результат. Пользователь может закрыть страницу или потерять соединение, а платёж может подтвердиться с задержкой или даже прийти повторно. Поэтому нельзя полагаться на один запрос от клиента.

В итоге процесс делится на две части. Сначала пользователь создаёт пожертвование и получает ответ, что платёж начат. Потом платёжный сервис отправляет результат, и система отдельно обрабатывает это событие и меняет статус на успешный или неуспешный.

## Выбор технологии

Для реализации асинхронной обработки результата пожертвования были рассмотрены RabbitMQ, Apache Kafka, NATS, WebSocket и gRPC streams. В данном сценарии требуется обработка отдельного события после получения callback от платёжного сервиса. Потоковая аналитика или постоянное соединение с клиентским интерфейсом здесь не используются.

Сравнение технологий приведено в таблице.

| Технология | Подходит для сценария | Причина выбора / отказа |
| - | - | - |
| RabbitMQ | Да | Поддерживает очереди сообщений, подтверждение обработки, повторную доставку и маршрутизацию событий между компонентами системы. |
| Apache Kafka | Скорее нет | Больше подходит для высоконагруженных потоков данных и хранения истории событий. Для обработки отдельных callback-сообщений использование Kafka выглядит избыточным. |
| NATS | Частично | Обеспечивает быстрый обмен сообщениями, но хуже подходит для сценариев, где важна гарантированная обработка сообщений и повторная доставка. |
| WebSocket | Нет | Используется для постоянного двустороннего соединения между клиентом и сервером. В данном случае такая связь не требуется. |

Для реализации был выбран RabbitMQ. В данном случае основной задачей является не обработка большого количества событий, а гарантированная передача сообщения между компонентами системы после получения callback от платёжного шлюза.

После получения callback сообщение помещается в очередь RabbitMQ, а дальнейшая обработка выполняется отдельным обработчиком. За счёт этого обработчик HTTP-запроса не выполняет всю бизнес-логику внутри одного запроса и может быстрее вернуть ответ платёжному сервису.

Также RabbitMQ поддерживает подтверждение обработки сообщений. Если во время обновления статуса пожертвования возникает ошибка, сообщение не теряется и может быть обработано повторно. Для данного сценария это важнее, чем высокая пропускная способность или хранение длинной истории событий.

При этом сам callback от платёжного сервиса уже является асинхронным взаимодействием. Если система обрабатывает небольшое количество платежей, статус пожертвования можно обновлять сразу после получения callback без использования брокера сообщений.

Использование RabbitMQ становится более оправданным, если требуется повысить устойчивость обработки, добавить повторные попытки выполнения и отделить получение события от бизнес-логики обновления данных.

В рамках проекта RabbitMQ используется для реализации асинхронной обработки события оплаты и демонстрации работы с брокером сообщений.

По формату контракта здесь логично использовать AsyncAPI, потому что обмен можно описать в JSON.

```yaml
asyncapi: 3.0.0
info:
  title: Donation Payment Result API
  version: 1.0.0
  description: Асинхронная обработка результата пожертвования после оплаты через внешний платёжный шлюз
defaultContentType: application/json
servers:
  rabbitmq:
    host: rabbitmq:5672
    protocol: amqp
    description: RabbitMQ broker
channels:
  donationPaymentResult:
    address: donation.payment.result
    messages:
      paymentResult:
        $ref: '#/components/messages/PaymentResultMessage'
operations:
  sendPaymentResult:
    action: send
    channel:
      $ref: '#/channels/donationPaymentResult'
    messages:
      - $ref: '#/channels/donationPaymentResult/messages/paymentResult'
  receivePaymentResult:
    action: receive
    channel:
      $ref: '#/channels/donationPaymentResult'
    messages:
      - $ref: '#/channels/donationPaymentResult/messages/paymentResult'
components:
  messages:
    PaymentResultMessage:
      name: PaymentResultMessage
      title: Payment result
      summary: Результат оплаты пожертвования
      payload:
        $ref: '#/components/schemas/PaymentResult'
  schemas:
    PaymentResult:
      type: object
      additionalProperties: false
      required:
        - eventId
        - donationId
        - paymentId
        - status
        - amount
        - currency
      properties:
        eventId:
          type: string
          description: Уникальный идентификатор события
          example: EVT-001
        donationId:
          type: string
          description: Идентификатор пожертвования в системе
          example: DON-001
        paymentId:
          type: string
          description: Идентификатор платежа во внешнем платёжном сервисе
          example: PAY-123456
        status:
          type: string
          description: Статус оплаты
          enum:
            - succeeded
            - failed
        amount:
          type: number
          format: double
          description: Сумма пожертвования
          example: 1000.0
        currency:
          type: string
          description: Валюта платежа
          example: RUB
        failureReason:
          type: string
          nullable: true
          description: Причина ошибки, если платёж неуспешен
          example: insufficient_funds
```
